Arch Compass reviews a Python repository's architecture: it detects boundary shapes deterministically, has a model judge each one against a written case and a policy corpus, asks the person only what neither code nor case can settle, and remembers every verdict, question, and decision as an immutable record. This page is the whole machine, drawn for making decisions about it — including what is half-built or stale.

01 · The shape

A strict hexagon, enforced by tests

Five layers with one composition root. The dependency rule is not convention — tests/unit/test_boundaries.py fails the build if domain/, ports/, or application/ import adapters, SQLite, httpx, or Typer, and it pins nineteen CLI commands and the web routes to their named services. It even pins one method's exact parameter list across three modules, so "the application assembles evidence" cannot drift silently.

domain/
Frozen pydantic aggregates, fingerprint algebra, and the pure derivations: finding detectors, atlas metrics, delta succession, verdict-cache keys, lineage ids.
ports/
13 persistence protocols plus analyzer, source reader, freshness, reasoning, investigation, VCS, archives.
application/
Reviews, cases, conversations, indexing, usage evidence, investigation toolbox, triage, CI, checkouts, examples, policies, rendering.
adapters/
The vendors: SQLite, Python AST (+optional mypy edge resolver), the three model providers, git, tarball fetcher, Markdown policy store.

02 · The review spine

One run, drawn with what it writes and when

Everything else in the product hangs off this flow (ReviewService.review). Two properties matter most: everything deterministic happens before a record exists — a run that would change nothing is refused, not stored — and everything a review depended on is pinned onto it at completion, so the record stays readable after the repository moves on.

What exists after a run

  • The review document — one JSON blob: every boundary with verdict, rationale, policy bearings, hinge; the overview; open questions; pinned code excerpts; the delta against the previous revision; the rendered Markdown; and the elicitation's investigation transcript.
  • The verdict cache — each fresh judgement stored under its full inputs identity, written even if the run later fails.
  • The boundary line — the branch's append-only ledger of succeeded / addressed / resurfaced events, written before the last model call.

03 · The evidence doctrine

§12.0 — who chooses what a model sees

The load-bearing rule of the whole design, amended once (this month) and test-enforced: the application decides what a verdict rests on; a model may look things up only where every lookup is recorded. Three stances, one per column:

StanceStagesMechanism
Shown, never fetchingjudgeApplication reads code at detector-chosen spans (definitions widened over their comment blocks, consumers attached as participants) into source_evidence. Tool-free by test. This is what keeps a verdict checkable by someone who wasn't there.
May look, all recordedelicit · both chat stagesTwo read-only tools (search_source, read_source), bounded (6 turns, 20k chars, caps per result), freshness-gated, first elicitation turn forced via Gemini mode ANY. Transcript stored on the review / message and disclosed in the UI.
Assembled evidence onlysummarise · answer/discuss inputsReviewEvidence is one application-built value: pinned case, pinned excerpts, elicitation round, atlas map. A question-scoped discussion sees only its cited boundaries (withheld verdicts can't leak) but may search the whole repo — verdicts aren't stored in source text.

Everything model-facing is positional: policies, boundaries and options are presented without identifiers, replies bind by position, and the application re-attaches identity afterwards. No model-authored key ever becomes a reference.

06 · Persistence

SQLite, one pattern throughout

One database per workspace (.archcompass/archcompass.db). Every aggregate is stored as a JSON blob beside queryable projection columns — the blob is the truth, columns exist for listings and joins. Connection-per-call, WAL, 5s busy timeout, foreign keys on. Migrations are numbered SQL files applied in one BEGIN IMMEDIATE each, with a checksum column that refuses to open a database whose applied migration was later edited.

Records

  • cases + case_revisions (snapshot + answered-provenance; one revision per review, enforced by index)
  • atlas_versions + nodes/edges/metrics/signals/module-facts
  • boundary_reviews (whole review as JSON) · review_conversations
  • verdict_cache · boundary_lines

Standing state

  • standing_decisions + decision_comments (append-only)
  • repository_lineages · branch_lineages
  • reasoning_model_choice (one row — workspace-global)
  • scope_selections · policy_source_registrations · source_origins
  • branch_baselines — orphaned; see the ledger

Policies are deliberately not stored: sources are registered by path and re-read per request (retrieval and its vector tables were removed after the embedding experiment lost to a per-pattern shortlist).

07 · Web surface & frontend

44 routes, two streams, six pages

All routes live in one FastAPI factory. A review runs synchronously inside its request — streaming is a worker thread feeding NDJSON lines; there is no job queue and therefore nothing to recover. Exactly two routes stream: the run itself and a chat message. Cancellation is out-of-band via the record. Errors are one ProblemDetail shape everywhere.

GroupGist
repositories / atlasindex (serialised by semaphore), start (index + open case), checkout/refresh, folder tree, explore (multiplexed atlas queries), review-context subgraph
casesCRUD + YAML import + history — mostly CLI/API-only today, no UI
reviewsrun + stream, list/detail (standings joined at read time), pinned source, markdown report, answers, cancel, delete
conversationscreate/list/get, message + streamed message (model-budget gated)
decisionsper-branch standings, single + bulk decide, history, comments
models / policies / examples / workspacelive probe + selection; policy CRUD + sources; bundled example load; one workspace summary row

Frontend in one breath

React + Vite + Tailwind v4 tokens, a vendored shadcn subset, and a generated OpenAPI type file with a drift gate. Six lazy pages; the review page is the centre of gravity (findings / questions / run log / atlas tabs). A run lives above the router (RunProvider) because it outlives the page that started it; every stream is read by one NDJSON reader. Design system: the sheet panel idiom, phoneFlush for full-bleed cards on phones, semantic verdict color families never reused for anything else, and an overflow-guard sweep test that fails any surface rendering unbounded text.

On multi-user (your last question, placed in this frame): the hosted mode is multi-user by isolation — visitors share nothing. A shared workspace is where the gaps live, and they are product-level, not SQLite: no identity, one global model-selection row, no per-branch run serialisation, answer races. WAL + short writes make the database itself a non-issue at team scale.

09 · The honest ledger

Half-built, dead, or lying documentation

Found by reading, not recalled. Ordered by how likely each is to mislead a decision.

  • Baseline is dead code with live storage. Domain, service, port, repository and the branch_baselines table all exist; nothing constructs or reaches them. architecture.md decision 4 retired the concept in favour of the delta rule — the code just hasn't been buried.
  • Two stale reference docs. persistence-model.md documents consultation-era tables dropped by migrations 010/017/020; domain-model.md describes types that no longer exist. architecture.md's closing paragraph still claims embedding-based retrieval its own body disavows.
  • A ghost package makes one guard vacuous. test_boundaries.py iterates workflows/, which was deleted; globbing a missing directory passes silently.
  • Streaming asymmetry (above): the only public deployment never streams.
  • Frontend drift hazards: atlas/policy types are hand-written beside the generated file (the exact drift its own comments warn about); seven dead client methods; several server routes have no UI at all (cases CRUD, decision history).
  • Small residue: a stale docstring pointing at a never-built application/preflight; consultation-era FailureDiagnostic still typed on reviews but unproducible; migration numbering skips 015; orphan __pycache__ directories for deleted modules; one comment/status-code disagreement on the checkout route; the INVESTIGATE_USAGE enum comment predates the persistence that landed the same day.

10 · Where decisions are open

The live decision surface

  • Multi-user / team use — identity, per-branch run lock, per-session model selection. The plan's own ordering (company-readiness) deferred auth last; the run lock is the smallest of the three and closes the ugliest race.
  • Review-flow organisation — architecture.md's "Under discussion" section holds the standing decisions (repository → branch → revisions; delta rule; baseline retired) with several of its open questions since answered by shipped code; it needs a reconciliation pass more than new decisions.
  • Measurement — the investigation/evidence work shipped with an eval fixture and a reading guide, but nothing quantitative runs routinely; judge variance across identical runs remains larger than most feature effects, so any prompt or evidence change still needs n≥10 discipline.
  • Product surface debt — cases have an API but no UI; the standalone atlas explorer was folded into the review page but its server surface remains; the second tab of a watched run shows counts without names.
  • Deferred by design — languages beyond Python, cost controls, procurement-grade data handling (named in company-readiness as "buyable, not demonstrable").
